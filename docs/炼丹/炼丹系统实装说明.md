# 炼丹系统实装说明

> 本文档记录 2026-08 炼丹系统实装（M1 核心机制 + M2 客户端 + M3 内容 + M3.5 分段工序 + M5 丹毒基础）的实际落地情况。
> 设计依据：《炼丹系统完整设计》《炼丹体系扩展设计》《炼丹内容实装册》。

## 一、需求

1. 炼丹成败由"人、地、火"五项评分决定：灵根匹配、神识、境界、环境灵气、工序操作；工序分（火候与投药）占 35%，环境占 20%，其余三项各占 15%。
2. 火候玩法：丹方定义多段火候曲线（文/中/武三带），炼制中可长按催火/收火/稳火，以灵力连续精调温度。
3. 严格保密原则：客户端绝不显示进度条、剩余时间、实时评分；只有"丹香"（成功前兆通知）与神识分级的目标火候带提示。
4. 失败分支：炸炉（早收/评分过低）、药渣（差一口气）、焦糊（收晚）、化灰（中途熄火）。
5. 丹药效果模型 v2：一颗丹可带多条效果（治疗/回灵/灌注修为/破境折扣/熟练度/寿元/清毒/辟谷等九类），按品阶缩放药力。
6. 丹毒体系：服丹积毒、自然衰减 + 打坐排毒，三档惩罚（药蚀/侵髓/毒发）；同类丹药短期重复服用产生抗药性递减。
7. 灌注修为丹存在每层 30% 硬上限，破境折扣只作用于"大境界突破"。
8. 一至三阶 15 张丹方 + 15 种丹药物品落地，全部走数据包 JSON（v2 schema）。
9. 空闲时先选已学丹方；可选 `feed_plan` 支持阶段投药，迟投降质、漏投固定药渣。聚气散保持一次投齐。

## 二、处理逻辑

### 评分与结算（服务端权威）
- `AlchemyResultCalculator`：五项评分纯函数 + `combine()` 加权合成总分与成功率（权重可在 CommonConfig 调整，权重和偏离 1 时回退默认 35/20/15/15/15）。
- 开炉时（`startRefining`）固定炼丹人 ID 并快照灵根/神识/境界评分，防止"高手代收丹"。
- 工序评分：无 `feed_plan` 时等于火候分；有计划时为 65% 火候 + 35% 投药精度，再占综合评分 35%。
- 品阶偏移：总分 ≥1 且原始命中 ≥0.9 出"完美 +2"，≥0.9 出 +1，≥0.75 平级，≥0.6 降一品，其余进失败分支。
- 收丹时机：`t<0.8` 炸炉，`0.8≤t<1.0` 药渣，`1.0≤t≤1.3` 正常窗口，`1.3<t≤1.6` 过火降品，`t>1.6` 焦糊；中途熄火化灰。

### 三式灵力控火
- 客户端长按催火/收火/稳火 → `MaintainHeatPacket(pos, mode)`；服务端逐 tick 校验菜单、距离、存活和炼制状态后扣费。
- 催火默认 +3/tick、收火 −4/tick、稳火锁当前档位中点；优先同系/相生灵力，任意池折算为 1.25 倍。
- 关界面、离炉、死亡、换维度、区块重载或灵力枯竭立即释放。

### 选方与阶段投药
- `SelectAlchemyRecipePacket` 只表达 recipeId，服务端重查学习状态、境界、炉内冲突和炼制状态。
- `feed_plan` 延后槽在开局封印，到指定阶段开放；最佳点 1.0、窗口边缘 0.7、同阶段迟投最低 0.25、跨阶段漏投固定药渣。
- 选方、已投/漏投/迟投掩码与投药累计分写 NBT；开放掩码重载后按服务端进度重新推导。

### 丹香通知
- 成功率达标时在有效时长 70%-90% 区间随机一次"丹香"toast（复用 `ShowNotificationPacket`），是唯一的进度前兆。

### 丹毒与抗药性
- `PlayerPillToxinData`（NBT 持久化，死亡克隆保留）：`addToxin` / 自然按天衰减 / 打坐每分钟额外排毒。
- 三档惩罚：≥40 药蚀（吸收与丹效打折）、≥70 侵髓（周期性反胃 debuff）、≥100 毒发（拒服丹药 + 周期扣血）。
- 抗药性：同 category 丹药在滚动窗口内重复服用效果递减，由 `useAndGetResistanceMultiplier` 结算。

### 效果分发
- `PillEffectApplier.apply()` 按 `AlchemyPillEffectData.type` 分发九类效果，全部乘以品阶药力倍率与抗药倍率；灌注修为受 `PlayerSpiritInfusionData` 30% 层上限约束；破境折扣写入 `PlayerBreakthroughDiscountData` 并在 `PlayerCultivationManager` 突破结算时消费（仅大境界）。

### 客户端 UI（AlchemyFurnaceScreen 重做）
- 已学丹方选择区、阶段工序 tooltip、延后槽“封/投/缺”覆盖层。
- 三段火候条 + 白色温度指针；催火/收火/稳火三个长按按钮与蓝色控火光。
- 目标火候带按神识分级：1-2 星不显示，3-4 星模糊边界（±40 热度渐变），5-7 星精确 + 换段前 2 秒闪烁预告。
- 目标带由客户端本地推算（开炉瞬间起表 + 材料匹配已学丹方 + 环境倍率缩放时长），中途打开界面只显示"?"。
- 左上角环境角标：主属性中文字 + ×倍率（绿/红/灰）；死地（倍率 0）禁用开始按钮。

### 调试命令
- `/ninecun_lingtai debug alchemy <recipeId> <count> [profile]`（OP2）：除 novice / novice_sloppy / expert 外，新增 heat_only / feed_only / feed_accuracy，输出火候、投药、工序及五项综合评分。

## 六、专用服务器适配与回归脚本

### 6.1 专用服务器 dist 崩溃修复（重要）

首次在 dedicated server（runServer）上启动时模组构造即崩溃：

- 崩溃点：ModNetwork.register 注册 OpenAlchemyRecipeImprintScreenPacket 时抛 BootstrapMethodError: Attempted to load class net/minecraft/client/gui/screens/Screen for invalid dist DEDICATED_SERVER。
- 根因：3 个 S2C 包（丹方拓印 / 功法拓印 / 道卷）的 handle 在 DistExecutor lambda 里直接 Minecraft.getInstance().setScreen(new XxxScreen(...))。字节码校验 setScreen 参数需要做子类型检查，必须加载 Screen 类，服务器上被 RuntimeDistCleaner 拒绝导致整个模组构造失败。而其余包 lambda 只调客户端管理类静态方法（invokestatic 不触发类型加载），因此安全。
- 修复：统一改走客户端管理类静态方法中转——
  - ClientAlchemyRecipeManager.openImprintScreen(hand, recipes)
  - ClientTechniqueManager.openImprintScreen(hand, techniques)
  - 新建 ClientDaoScrollScreenManager.open(snapshot, editingSelf)
- **代码规范**：网络包 handle 的 lambda 中禁止直接 new Screen / 调 setScreen，一律经客户端管理类静态方法中转。

### 6.2 runServer 与纯客户端第三方模组

开发依赖中的纯客户端渲染模组（oculus、bettergrassify、embeddium、rrls、modelfix、entityculling、distant_horizons、particle_core、bad_optimizations、in_game_account_switcher、inventory-tabs）无 dist 保护，dedicated server 上会崩。`build.gradle` 现用 `serverRegression` 属性条件隔离：普通客户端开发依赖不变，回归脚本自动传 `-PserverRegression=true`，无需再临时改文件。

### 6.3 回归执行方式

gradle runServer 不转发 stdin，控制台注入命令无效；改用 RCON：

`
python scripts/run_server_regression_rcon.py
`

脚本自动开启 `run/server.properties` 的本地 RCON、隔离纯客户端模组并启动服务器；就绪后按画像批量执行 `/ninecun_lingtai debug alchemy <丹方> <次数> <画像>`，断言响应完整性、抽样偏差、旧丹方兼容、65/35 工序权重和画像排序，再 stop 优雅关服。结果落盘 `run/regression_rcon_<时间戳>.log`。
